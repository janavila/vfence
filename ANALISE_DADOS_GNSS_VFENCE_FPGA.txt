CONCLUSÃO EXECUTIVA

1. O firmware ativo da coleira é geofence/VFenceCollarLoRa/VFenceCollarLoRa.ino.
2. O GNSS usa HardwareSerial UART1, RX GPIO23, 115200 baud, 8N1, somente recepção.
3. TinyGPSPlus recebe caracteres individuais. O código não preserva sentenças brutas nem horário GNSS.
4. Do GNSS, o firmware ativo consulta somente localização (lat/lon), validade/atualização da localização,
   satélites e HDOP. Altitude, velocidade, curso, data e hora não são consultados.
5. Lat/lon passam de double em graus para int32_t E7 antes do pacote LoRa.
6. A telemetria LoRa é binária, não texto e não JSON: header de 5 bytes + payload de 18 bytes.
7. O Gateway converte E7 de volta para graus e acrescenta RSSI e SNR medidos pelo receptor LoRa.
8. Gateway -> Base usa JSON por linha com prefixo [APP] e schema vfence.gateway.serial.v1.
9. A Base reduz inside/near/veryNear/gpsValid a uma única zona e descarta distanceBorderM.
10. SQLite local não possui colunas para battery_pct, fence_version, distanceBorderM, gpsValid,
    inside, near ou veryNear. Battery/fenceVersion seguem para a outbox, mas não para telemetry local.
11. PostgreSQL recebe lat, lon, zone, satellites, hdop, battery_pct, fence_version, rssi e snr.
    Não recebe sequence, distanceBorderM, gpsValid, inside, near ou veryNear.
12. RSSI/SNR não vêm do GPS. São medidos por pacote no Gateway com LoRa.packetRssi()/packetSnr().
13. Não existem contadores agregados de TX, RX, ACK, NACK, retries, timeouts ou duplicatas.
    Portanto PDR/PER não podem ser calculados corretamente com a instrumentação atual.
14. Não foi encontrado código FPGA, driver FPGA, barramento FPGA ou processo de alimentação do FPGA.

2. GNSS NA COLEIRA
============================================================

ARQUIVO: geofence/VFenceCollarLoRa/collar_config.h (aprox. linhas 9-11)
ARQUIVO: geofence/VFenceCollarLoRa/VFenceCollarLoRa.ino (linhas 19-21, 849-890, 896-955)

Interface: UART via HardwareSerial.
Objeto: HardwareSerial GPSserial(1), portanto UART1 do ESP32.
Configuração: GPSserial.begin(GPS_BAUD, SERIAL_8N1, GPS_RX, -1).
Baud: 115200.
Pino: RX do ESP32 = GPIO23; comentário: TX do GPS -> GPIO23. TX do ESP32 = -1, não usado.
Biblioteca: TinyGPSPlus, objeto TinyGPSPlus gps.

Formato bruto:
- O loop lê GPSserial.read() e entrega cada byte/caractere a gps.encode().
- TinyGPSPlus é usada como parser de fluxo textual GNSS/NMEA.
- O código não configura modo binário UBX e não trata frames binários.
- O repositório não captura exemplos de sentenças brutas nem verifica tipos GGA/RMC.
- Portanto: fluxo de caracteres compatível com NMEA é a expectativa do código; as sentenças exatas
  produzidas pelo módulo físico não são comprováveis apenas pelo repositório.

Mensagem NMEA original: NÃO É MANTIDA. Não há buffer, log ou persistência das sentenças.

Campos/estados TinyGPSPlus realmente consultados:
- gps.location.isUpdated() -> bool; dispara processNewGpsPosition.
- gps.location.isValid() -> bool; exige fix/localização válida.
- gps.location.lat() -> double; latitude em graus.
- gps.location.lng() -> double; longitude em graus.
- gps.satellites.isValid() -> bool.
- gps.satellites.value() -> valor tratado como uint32_t.
- gps.hdop.isValid() -> bool.
- gps.hdop.hdop() -> double.

Tempo/idade usado pelo firmware:
- lastValidGpsMs, gpsMonitorStartMs e millis() são relógio monotônico do ESP32, NÃO horário GNSS.
- positionAgeSeconds() mede segundos desde o último fix válido usando millis().

Campos não consultados em nenhum ponto do firmware ativo:
- altitude;
- velocidade;
- curso/heading;
- data GNSS;
- hora GNSS;
- idade fornecida pela própria biblioteca para o campo location;
- número de caracteres processados/checksum failed/sentences with fix;
- precisão estimada horizontal/vertical além de HDOP.

DADOS DISPONÍVEIS NA BIBLIOTECA MAS NÃO USADOS PELO VFENCE

O projeto não inclui o fonte da versão instalada de TinyGPSPlus; por isso a auditoria não atribui
tipos/garantias a APIs externas não presentes no repositório. É comprovado somente que o código VFence
não referencia altitude, speed, course, date, time nem estatísticas do parser. Essas famílias são comuns
em TinyGPSPlus, mas sua disponibilidade exata deve ser confirmada na versão instalada antes de um projeto futuro.

4. TRANSFORMAÇÕES DOS DADOS
============================================================

LATITUDE/LONGITUDE DE TELEMETRIA
double graus (TinyGPSPlus)
-> degreesToE7: llround(graus * 10.000.000)
-> int32_t CoordinateE7
-> writeI32BE: 4 bytes signed em big-endian por coordenada
-> LoRa
-> readI32BE no Gateway
-> e7ToDegrees: double = E7/10.000.000
-> Serial.print(..., 7): JSON decimal com 7 casas ou null
-> json.loads: float Python ou None
-> SQLite REAL/NULL
-> JSON batch: número/JSON null
-> PostgreSQL DOUBLE PRECISION/NULL.

HDOP
double gps.hdop.hdop()
-> multiplicação por 100, lround
-> uint16_t hdopX100; 0xFFFF significa indisponível
-> 2 bytes big-endian
-> Gateway divide por 100.0 e imprime 2 casas
-> float Python
-> SQLite REAL
-> PostgreSQL DOUBLE PRECISION.
Perda deliberada de resolução: centésimos de HDOP.

SATÉLITES
valor TinyGPSPlus tratado como uint32_t
-> clamp máximo 254
-> uint8_t; 0xFF significa indisponível
-> 1 byte
-> JSON inteiro/null
-> Python int/None
-> SQLite/PostgreSQL INTEGER/NULL.

DISTÂNCIA À BORDA
double latestGeofence.distanceBorderM
-> clampDistanceMeters + lround
-> uint16_t metros inteiros; 0xFFFF indisponível
-> JSON distanceBorderM inteiro/null no Gateway
-> DESCARTADA por SerialReader._telemetry_packet.

ESTADOS BOOLEANOS
GeofenceResult + estados do dispositivo
-> buildStateFlags() em uint8_t:
bit0 inside, bit1 near, bit2 veryNear, bit3 gpsValid, bit4 lowBattery,
bit5 criticalBattery, bit6 buzzer, bit7 segundo atuador
-> Gateway expõe somente inside/near/veryNear/gpsValid em JSON
-> Base converte os quatro para uma zone:
   !gpsValid=GNSS_INVALIDO; !inside=FORA; veryNear=CRITICO; near=ATENCAO; senão SEGURO.
-> flags de bateria/atuadores não chegam à Base.

CERCA CENTRAL -> COLEIRA (não é dado GNSS, mas esclarece E6/E7)
Central e SQLite local: int E6
-> Base divide por 1.000.000 e envia graus decimais em FENCE_POINT
-> Gateway degreesToE7 multiplica por 10.000.000
-> LoRa/coleira usam int32_t E7.

============================================================
5. COLEIRA -> PACOTE LoRa: TELEMETRY/POSITION_STATUS
============================================================

ARQUIVO: vfence_protocol.cpp, encodeTelemetry (aprox. linhas 305-325)
ARQUIVO: VFenceCollarLoRa.ino, sendTelemetryPacket (linhas 548-573)

O pacote tem 23 bytes: header 5 + payload 18. Ordem em rede big-endian.

HEADER (5 bytes)
byte 0: control — versão 2 bits, MessageType 2 bits, ACK_REQ, RETRY, URGENT, reservado.
byte 1: collarId uint8_t.
bytes 2-3: sequence uint16_t big-endian.
byte 4: payloadLength uint8_t (=18).

PAYLOAD POSITION_STATUS (18 bytes)
offset | bytes | campo | tipo wire | unidade | categoria/fonte
0 | 1 | subtype=0x01 | uint8 | enum | D protocolo
1 | 4 | latitude | int32 E7 BE | 1e-7 grau | A GNSS
5 | 4 | longitude | int32 E7 BE | 1e-7 grau | A GNSS
9 | 2 | distanceBorderM | uint16 BE | metro inteiro | B geofencing
11 | 1 | batteryPct | uint8 | % ou 0xFF | C dispositivo
12 | 1 | satellites | uint8 | contagem ou 0xFF | A GNSS
13 | 2 | hdopX100 | uint16 BE | HDOP x100 ou 0xFFFF | A GNSS
15 | 1 | stateFlags | bitset uint8 | estados | B/C
16 | 2 | fenceVersion | uint16 BE | versão | C configuração

sequence está no header, não no payload. Telemetria não solicita ACK (ackReq=false) e não usa retry.
batteryPct: PARCIAL. A variável existe, mas permanece U8_UNAVAILABLE porque a leitura de bateria
está explicitamente comentada como ainda não integrada.

============================================================
6. TELEMETRIA E EVENTOS, SEPARADOS
============================================================

TELEMETRY / POSITION_STATUS — IMPLEMENTADO
Produção: periódica, telemetryIntervalS (padrão 10 s) + jitter aleatório 0..3 s.
Confiabilidade: sem ACK/retry.
Campos: todos os 18 bytes descritos acima.

EVENT OUTSIDE/BACK_INSIDE — IMPLEMENTADO
Payload 17 bytes: subtype(1), fenceVersion(2), lat E7(4), lon E7(4),
distanceBorderM(2), batteryPct(1), satellites(1), hdopX100(2).
ACK_REQ=true, URGENT=true; usa sendReliable.

EVENT GPS_LOST — IMPLEMENTADO
Payload 11 bytes: subtype(1), lastLatitude E7(4), lastLongitude E7(4), positionAgeS(2).
Disparado após gpsTimeoutS sem fix (padrão 60 s). ACK_REQ/URGENT.

EVENT GPS_RECOVERED — IMPLEMENTADO
Payload 12 bytes: subtype(1), latitude E7(4), longitude E7(4), satellites(1), hdopX100(2).
Disparado no primeiro fix após estado perdido. ACK_REQ, não urgente.

EVENT DEVICE_STARTED — IMPLEMENTADO
Payload 5 bytes: subtype(1), resetReason(1), activeFenceVersion(2), batteryPct(1).
É enviado no setup. resetReason está fixo em POWER_ON; leitura real de esp_reset_reason NÃO IMPLEMENTADA.

EVENT LOW_BATTERY/CRITICAL_BATTERY — PROTOCOLO SUPORTA, MAS NÃO PRODUZIDO
Encoder, decoder e parser do Gateway existem. Não foi encontrada chamada a encodeBatteryEvent no
firmware ativo. batteryPct permanece indisponível. Portanto esses eventos não são gerados hoje.

Perdas no Gateway ao converter EVENT para JSON:
- OUTSIDE/BACK_INSIDE: LoRa contém battery/satellites/hdop; JSON omite os três.
- GPS_RECOVERED: LoRa contém satellites/hdop; JSON omite os dois.
- Eventos não incluem RSSI/SNR no JSON, embora o Gateway os tenha medido para o pacote.
- Alguns JSONs de evento não incluem sequence; somente OUTSIDE/BACK_INSIDE o incluem atualmente.

============================================================
7. O QUE REALMENTE VIAJA PELO LoRa
============================================================

Resposta explícita: bytes binários. Não é texto e não é JSON.

ESP32 coleira
-> preenche struct C++ (ex.: TelemetryPayload)
-> encodeTelemetry/encode* escreve uint8_t packet[MAX_PACKET_SIZE]
-> inteiros multibyte em big-endian
-> transportSend chama LoRa.beginPacket(), LoRa.write(data,len), LoRa.endPacket()
-> SX1276 transmite.

MAX_PACKET_SIZE=64. HEADER_SIZE=5. PROTOCOL_VERSION=0 (wire v1 do projeto).
O subtipo é o primeiro byte de cada payload.
Exemplo comprovado pelo layout, para telemetria: 5 bytes header + 18 bytes payload = 23 bytes.

============================================================
8. GATEWAY: RECEPÇÃO E QUALIDADE DO ENLACE
============================================================

ARQUIVO: gateway/VFenceGateway/VFenceGateway.ino

1. pollLoRaReceive chama LoRa.parsePacket().
2. Bytes entram em uint8_t data[MAX_PACKET_SIZE], preenchido por LoRa.read().
3. Após drenar o pacote, coleta:
   - const int rssi = LoRa.packetRssi(); unidade exibida dBm;
   - const float snr = LoRa.packetSnr(); unidade exibida dB.
4. processIncomingPacket chama decodePacket, que reconstrói PacketView/Header.
5. header.type identifica TELEMETRY/EVENT/CONTROL/CONFIG.
6. processTelemetry confirma subtype POSITION_STATUS e chama decodeTelemetry.
7. processEvent/processEventPayload escolhe EventSubtype e decoder correspondente.

Alterações feitas pelo Gateway:
- E7 -> graus decimais para JSON;
- sentinelas COORD_UNAVAILABLE/U8_UNAVAILABLE/U16_UNAVAILABLE -> null;
- stateFlags -> booleanos inside/near/veryNear/gpsValid;
- acrescenta RSSI/SNR somente ao JSON de telemetria recebida fisicamente;
- acrescenta estado ONLINE/OFFLINE e lastSeen em memória.

RSSI/SNR são medidos por pacote recebido no Gateway. NÃO são GNSS e NÃO são calculados pela coleira.
Pacotes injetados pelo comando RX usam hasRadioMetrics=false, portanto rssi/snr são omitidos.

============================================================
9. GATEWAY -> BASE: vfence.gateway.serial.v1
============================================================

Gateway gera JSON manualmente com Serial.print, prefixo [APP] e newline por Serial.println.
Baud USB/Serial: 115200 (setup, Serial.begin).
Comandos de entrada têm limite 512 caracteres. Não existe verificação equivalente explícita para
linhas [APP] de saída, mas as mensagens geradas são curtas e limitadas pelos campos fixos.

TELEMETRIA [APP] contém:
schema string; kind string; collarId inteiro; sequence inteiro;
latitude número/null; longitude número/null; distanceBorderM inteiro/null;
battery inteiro/null; satellites inteiro/null; hdop número/null;
inside bool; near bool; veryNear bool; gpsValid bool; fenceVersion inteiro;
rssi inteiro e snr número quando hasRadioMetrics=true; caso contrário são OMITIDOS.

Exemplo realista baseado exatamente nas chaves e formatação do código:
[APP] {"schema":"vfence.gateway.serial.v1","kind":"telemetry","collarId":1,
"sequence":27,"latitude":-31.3054583,"longitude":-54.0643931,
"distanceBorderM":12,"battery":null,"satellites":10,"hdop":0.90,
"inside":true,"near":true,"veryNear":false,"gpsValid":true,
"fenceVersion":2,"rssi":-65,"snr":9.25}
Na Serial real isso é uma única linha, sem as quebras usadas acima para leitura.

não estruturado, e somente os campos que o Gateway colocou no JSON.

16. "PEGAR DO BANCO PARA O FPGA"
============================================================

1. Primeiro ponto de disponibilidade na Raspberry:
SerialReader.process_line/_process_gateway_app, no dict retornado por json.loads, antes do SQLite.

2. Dados em memória antes do SQLite: SIM. O dict [APP] e o ParsedPacket existem em memória;
_save_and_broadcast chama Database.save_packet depois da conversão.

3. Enviar diretamente do processo Python ao FPGA futuramente: tecnicamente possível, pois o ponto
de interceptação existe. NÃO IMPLEMENTADO: não há driver, SPI/UART/PCIe/GPIO, fila ou protocolo FPGA.

4. Se a leitura fosse do SQLite:
- telemetry: lat/lon/zone/satellites/hdop/rssi/snr/sequence/hora;
- collars: último valor desses campos;
- central_outbox, antes do ACK: também battery_pct/fence_version em data_json;
- events: somente mudanças de zone;
- não há distanceBorderM nem booleanos originais.

5. PostgreSQL é remoto quando Central está na nuvem. Depender dele introduziria internet e ida/volta
HTTPS, contrariando a autonomia local existente. Isso não decide a arquitetura, apenas registra o efeito.

COMPARAÇÃO
A) SerialReader/memória -> FPGA
latência: menor; internet: nenhuma; complexidade: driver/fila novos; dados: conjunto [APP] completo,
inclusive distanceBorderM antes do descarte; autonomia: preservada; histórico/replay: precisa ser criado.

B) SQLite local -> FPGA
latência: baixa/moderada; internet: nenhuma; complexidade: consultas/controle de cursor;
dados: somente campos persistidos; autonomia: preservada; histórico: já existe; há perdas de campos.

C) PostgreSQL/Central -> FPGA
latência: maior e variável; internet: obrigatória; complexidade: autenticação/API/consulta;
dados: campos do batch, sem sequence/distance/flags; autonomia: reduzida; histórico remoto disponível.

============================================================
18. O QUE FALTA PARA PDR/PER
============================================================

PDR = RX/TX e PER = perdidos/enviados exigem denominador TX conhecido e definição clara de janela,
origem/destino, tipo de pacote e tratamento de retransmissões.

Já existe:
- sequence uint16 por emissor;
- indicador RETRY no header;
- transmissions por mensagem confiável enquanto pendente;
- ACK/NACK e timeout/retry para mensagens confiáveis;
- deduplicação de até 16 EVENTs recentes no Gateway;
- RSSI/SNR do pacote recebido.

Não existe:
- contador TX total por coleira/tipo/janela;
- contador RX total válido/inválido;
- contador de pacotes perdidos;
- contadores ACK/NACK/retry/timeout/duplicata;
- contagem de CRC físico rejeitado;
- persistência e timestamps de envio/ACK;
- identidade de sessão robusta além de DEVICE_STARTED/limpeza de histórico;
- exposição estruturada dessas métricas à Base.

Sequence sozinha não resolve: reinicia no boot, faz wrap em uint16 e é compartilhada por telemetria,
eventos e controle. Uma lacuna entre duas telemetrias pode ser um evento válido, não perda.

Pontos futuros onde seria tecnicamente possível instrumentar, sem implementação nesta tarefa:
- transportSend/sendReliable/serviceReliableTx na coleira e Gateway para TX/retry/timeout;
- pollLoRaReceive/processIncomingPacket no Gateway para RX válido/inválido;
- acknowledgeReliable/rejectReliable/processEvent para ACK/NACK/duplicata;
- uma nova mensagem [APP] de métricas ou extensão de status para a Base;
- SQLite local para séries temporais. Nenhuma dessas extensões existe hoje.

21. RESUMO PARA DISCUSSÃO COM O GRUPO
============================================================

A) GNSS usado: lat, lon, validade/atualização, satélites e HDOP. Sem altitude, velocidade, curso,
data/hora ou NMEA persistida.

B) Geofencing: inside, distância à borda e proximidade FAR/NEAR/VERY_NEAR; Base deriva cinco zonas.

C) LoRa disponível: RSSI e SNR por pacote no Gateway; parâmetros de rádio fixos/configurados.

D) Protocolo: sequence, flags, ACK/NACK, retry temporário, deduplicação de EVENT e erros de cerca.

E) Gateway recebe payload binário com posição/geofence/dispositivo e acrescenta RSSI/SNR.

F) Base recebe JSON estruturado. Antes do SQLite, possui distanceBorder e booleanos; depois os reduz.

G) SQLite guarda lat/lon/zone/satélites/HDOP/RSSI/SNR/sequence/raw e horários de chegada.
Battery/fenceVersion ficam só na outbox enquanto pendentes.

H) Central/PostgreSQL recebe lat/lon/zone/satélites/HDOP/bateria/fenceVersion/RSSI/SNR.
Não recebe sequence, distanceBorder ou flags originais.

I) Somente em memória: NMEA sendo parseada; GeofenceResult double; contadores transmissions por
mensagem; bitmap/duplicatas; lastSeen do Gateway; collar_status; dict [APP] completo.

J) Candidatos naturais existentes para estudo futuro, sem decisão: lat/lon, satélites, HDOP,
distanceBorder, zona/flags, RSSI, SNR, sequence, retry/ACK/timeout quando instrumentados.

K) Falta instrumentar: TX/RX totals, perdas, ACK/NACK/retry/timeout/duplicata agregados, latência ACK,
CRC físico rejeitado, sessões/janelas e persistência dos campos descartados.
